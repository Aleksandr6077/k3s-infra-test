# ADR-01: Вынужденный отказ от 3-зонного HA (Multi-Zonal)

- **Status:** Accepted
- **Date:** 2026-10-30
- **Deciders:** [@Aleksandr6077]
- **Context:** Yandex Cloud, K3s HA-кластер, эфемерный стенд

---

## Context

На момент создания проекта кластер был спроектирован под **3 зоны доступности**
(`ru-central1-a`, `ru-central1-b`, `ru-central1-d`) — для нечётного кворума
etcd (2 из 3) и отказоустойчивости при потере одной зоны.

В процессе работы зона `ru-central1-b` стала недоступна для размещения
новых ресурсов. Попытка использовать `ru-central1-e` уперлась в лимиты
квот. Служба поддержки Yandex Cloud официально рекомендовала использовать
только `ru-central1-a` и `ru-central1-d` до восстановления.

**Ключевые ограничения:**

- **Квота `compute.ssdDisks.size`:** в зоне `ru-central1-e`
  исчерпана. Без свободной квоты нельзя создать диск для третьей
  мастер-ноды.
- **Бюджет:** стенд эфемерный (~20-40 ₽ за 2 часа). Переход на `Dedicated Hosts`
   — нецелесообразны в условиях пет-проекта.

---

## Decision

Кластер K3s разворачивается в **двух** зонах доступности
(`ru-central1-a` и `ru-central1-d`) вместо трёх.

**Что меняется:**

- Количество мастер-нод: **3 → 2**.
- Количество зон: **3 → 2**.
- Воркеры остаются в двух зонах (`a` и `d` — в зависимости
  от доступных квот).

---

## Consequences

### Положительные

- Стенд **работает** в текущих ограничениях облака.
- Стоимость остаётся в бюджете эфемерного проекта.
- Не блокирует работу над P0/P1 (Data Layer, Observability).

### Отрицательные (Риски)

#### 1. Кворум etcd (Raft) — 2 из 2

В конфигурации с 2 мастерами кворум составляет **2 из 2**. Это означает
**нулевую толерантность к отказам** — любая потеря одной мастер-ноды
(или зоны) лишает etcd кворума.

**Что происходит при потере кворума:**

- API-сервер не может читать актуальное состояние из etcd.
- Поды продолжают работать.
- Любые операции с API (`kubectl get`, `kubectl apply`, ArgoCD sync)
  падают с ошибкой `etcdserver: no leader` или `context deadline exceeded`.
- Кластер фактически «заморожен» до восстановления кворума.

#### 2. Отказ зоны

Падение зоны `ru-central1-a` или `ru-central1-d` гарантированно
парализует управление кластером (потеря кворума etcd).

#### 3. Preemptible

Внезапное отключение мастер-ноды (`preemptible = true`) — **главная
причина потери кворума**. На 2 мастерах это особенно критично: любой
реклейм одной из двух нод = потеря кворума.

#### 4. Multi-Zonal scheduling

Без Yandex CCM поды и тома не распределяются по зонам. Даже в 2 зонах
кластер не гарантирует, что поды не уедут в одну зону.

---

## Alternatives Considered

### 1. Дождаться восстановления квот

**Плюсы:** истинный 3-зонный HA.

**Минусы:** блокирует работу на неопределённый срок. Не подходит для
пет-проекта, который нужно двигать.

**Вердикт:** отклонено.

### 2. Dedicated Hosts для обхода лимитов

**Плюсы:** выделенные физические серверы, нет оверкоммита.

**Минусы:** другой ценовой сегмент (в разы дороже). Не «обход лимитов»,
а **другой продукт**. Для эфемерного стенда — нецелесообразно.

**Вердикт:** отклонено.

### 3. Одна зона, 3 мастера

**Плюсы:** нечётный кворум (3 из 3), нет проблем с квотами по зонам
(все в одной).

**Минусы:** потеря зоны = потеря всего кластера. Для HA это **хуже**,
чем 2 зоны с 2 мастерами.

**Вердикт:** отклонено. 2 зоны с 2 мастерами дают хотя бы **зонную**
изоляцию (хотя кворум всё равно 2 из 2).

---

## Production Path

Для перехода в состояние истинного `HA (High Availability)` необходимо:

1. **Дождаться стабилизации облака** или увеличить квоты
   `compute.ssdDisks.size` в **трёх** зонах.
2. **Вернуть `count = 3`** для мастер-нод в `main.tf`.
3. **(Опционально) Отказаться от `preemptible = true`** для мастер-нод,
   так как внезапное отключение ВМ — главная причина потери кворума.
4. **(Опционально) Внедрить Yandex CCM** для topology-aware scheduling
   по зонам — чтобы поды и тома распределялись корректно.

**Критерий возврата:** 3 мастер-ноды в 3 зонах, кворум 2 из 3,
потеря одной зоны не ломает кластер.
