# 🔍 Инфраструктурный аудит: Узкие места, компромиссы и техдолг

Этот документ содержит инженерный анализ текущей архитектуры
эфемерного стенда. Все ограничения разделены по уровням критичности.
Для каждого пункта верхнеуровнево описано production-решение.

---

## 🔴 [  ] P0: Критические риски и архитектурные ограничения

*   **Отсутствие Kubernetes CCM (Cloud Controller Manager)**
    *   **Проблема:** Кластер не интегрирован с API Yandex Cloud. Ноды не получают метки зон доступности (`topology.kubernetes.io/zone`), из-за чего встроенный планировщик (`Scheduler`) не может гарантировать корректное распределение реплик (`PodAntiAffinity`) по физическим дата-центрам.
    *   **Production-решение:** Внедрение `Yandex Cloud Controller Manager`.
*   **Связанность Control Plane и State (Embedded etcd)**
    *   **Проблема:** База данных кластера (`etcd`) запущена внутри бинарника k3s на тех же мастер-нодах, где работают `API-server` и `Controller Manager`. Высокая нагрузка на `API-server` может привести к деградации `etcd` и отказу всего кластера.
    *   **Production-решение:** Вынос `etcd` на выделенный, изолированный кластер нод.
*   **Компромисс отказоустойчивости хранилища Longhorn**
    *   **Проблема:** Для экономии ресурсов на слабых прерываемых (`preemptible`) нодах настроено 2 реплики данных вместо 3. Это повышает риск возникновения Split-Brain и полной потери данных при одновременном сбое двух нод.
    *   **Production-решение:** Миграция Stateful-нагрузок на стандартные (On-Demand) ВМ и увеличение количества реплик до 3.
*   **Ограничение CSI-драйвера по типу монтирования (RWO)**
    *   **Проблема:** Longhorn тома работают в режиме ReadWriteOnce. При стратегии деплоя Rolling Update новые поды не могут подняться на других ноды до тех пор, пока старые поды не освободят диск, что приводит к зависанию деплоя (`Multi-Attach error`).
    *   **Production-решение:** Изменение стратегии деплоя на `Recreate` или настройка встроенного NFS-сервера Longhorn для поддержки RWX (ReadWriteMany).

## 🟡 [  ] P1: Проблемы безопасности и автоматизации

*   **Нарушение декларативности GitOps для секретов**
    *   **Проблема:** Использование Ansible Vault для шифрования токенов и паролей отсекает ArgoCD от управления секретами. Секреты деплоятся «руками» через Ansible в обход Git.
    *   **Production-решение:** Внедрение Mozilla SOPS (с шифрованием в Git) или External Secrets Operator в связке с HashiCorp Vault / Yandex Lockbox.
*   **Смешение зон ответственности (Ansible vs GitOps)**
    *   **Проблема:** Системные компоненты кластера (Longhorn) устанавливаются через Ansible-плейбуки. Это создает риск дрейфа конфигурации (Configuration Drift).
    *   **Production-решение:** Управление Longhorn строго через ArgoCD (паттерн App-of-Apps).
*   **Сетевой тупик для CI/CD (Bastion-only доступ)**
    *   **Проблема:** Закрытый снаружи API-сервер (порт 6443) делает невозможным использование публичных раннеров (GitHub Actions / GitVerse) для автоматического деплоя без VPN.
    *   **Production-решение:** Развертывание саморегистрирующихся воркеров внутри приватного контура (Actions Runner Controller — ARC).
*   **Бастион как Единая точка отказа (SPOF)**
    *   **Проблема:** Доступ к кластеру завязан на один Bastion-хост, развернутый на прерываемой (Preemptible) ВМ. Его остановка облаком в момент деплоя заблокирует административный доступ.
    *   **Production-решение:** Развертывание бастиона на стандартной ВМ или поднятие отказоустойчивого VPN-шлюза в VPC.

## 🟢 [  ] P2: Недостатки наблюдаемости (Observability)

*   **Отсутствие централизованного логирования**
    *   **Проблема:** Стек Loki/Promtail удален. Инфраструктура «слепа» к логам приложений, доступен только сбор метрик через Prometheus.
    *   **Production-решение:** Развертывание агентов Vector / Alloy / Promtail и сбор логов в Loki или ClickHouse.
*   **Отсутствие локального DNS-резолва**
    *   **Проблема:** Для проверки Ingress-маршрутизации (L7) приходится вручную подменять HTTP-заголовки `Host` в `curl`для отладки.
    *   **Production-решение:** Поднятие локального dnsmasq или CoreDNS на управляющем хосте разработчика.
