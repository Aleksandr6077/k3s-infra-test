K3s: Деплой, Мониторинг и Логирование

Пошаговый проект по развертыванию веб-приложения в легковесном Kubernetes (K3s) с настройкой базового мониторинга и сбором логов. 

## ⚙️ Что внутри проекта
* **Кластер**: K3s
* **Приложение**: Веб-сервер Nginx (с ограничением по CPU/памяти и постоянным диском)
* **Мониторинг**: Prometheus + Grafana (установка через Helm)
* **Логирование**: Grafana Loki + Promtail (установка через Helm)

---

## 🛠️ Как это устроено (По шагам)

### 1. Подготовка окружения (CLI)
Чтобы не писать длинные команды, настроил алиас для kubectl и скопировал конфиг для доступов:
```bash
alias k='k3s kubectl'
mkdir -p ~/.kube && sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown $(id -u):$(id -g) ~/.kube/config
```
Для удобного просмотра подов в терминале установил утилиту **K9s**.

### 2. Запуск приложения (`apps/my-nginx/app.yaml`)
Монолитный YAML-манифест, который поднимает:
* **Deployment**: Запускает контейнер Nginx. Прописал ему лимиты ресурсов (`limits: memory: 64Mi`), чтобы контейнер не сожрал всю память сервера.
* **Service & Ingress**: Маршруты, чтобы пустить трафик к сайту.
* **PersistentVolumeClaim (PVC)**: Подключил к Nginx постоянный диск на 1 Гб (`storageClassName: local-path`), чтобы файлы сайта (index.html) не стирались при перезапуске контейнера.

### 3. Мониторинг (Prometheus + Grafana)
Поставил стек `kube-prometheus-stack` через Helm. Настроил кастомный конфиг `mon-values.yaml`:
* Отключил тяжелый `node-exporter` (сбор метрик самого железа хоста), так как в моей изолированной среде он падал с ошибкой прав монтирования. Оставил только метрики самого Kubernetes.
* Задал пароль `admin/admin` для входа.

### 4. Сбор логов (Loki + Promtail)
* Поставил базу данных логов **Loki** в легком режиме `SingleBinary` (конфиг `loki-values.yaml`).
* Поставил агента **Promtail**, который собирает текстовые логи со всех контейнеров и шлет их в Loki.
* Подключил Loki как Data Source внутри Grafana.

## 🛡️ Локальная безопасность и валидация (Pre-commit | Trivy)
В проекте настроена автоматическая проверка кода перед коммитом с помощью pre-commit хуков.
Подключенные хуки:
* docker-compose-check — автоматическая валидация структуры и синтаксиса файлов Docker Compose.
* Check for Hardcoded Secrets — Trivy (.trivyignore сознательно использую)

## ⚙️ Автоматизация и CI/CD (Gitea Actions)
В проекте настроен автоматический пайплайн валидации изменений (`.gitea/workflows/simple-workflow.yaml`), который триггерится на каждый push в ветку master.
### Этапы пайплайна (Job: validate):
* **Secret Scanning:** Автоматический аудит истории коммитов на утечку паролей с помощью `Gitleaks`.
* **Linting & Syntax:** Автоматическая проверка синтаксиса YAML-манифестов с помощью `pyyaml`.
* **Kubernetes Dry-Run:** Проверка структуры и соответствия манифестов стандартам K8s с помощью `kube-linter` перед деплоем в кластер.

## 🔍 Как я это проверял (Траблшутинг)

* **Костыль для проверки домена**: Когда проверял работу Ingress, домен `my-app.local` не резолвился через DNS хоста. Чтобы доказать, что Ingress работает - делаю curl-запрос, принудительно передав заголовок хоста на localhost:
  ```bash
  curl -H "Host: my-app.local" http://127.0.0.1
  ```
* **Проверка Графаны с Windows**: Так как K3s крутится на отдельном сервере, я проверял графики и логи со своей рабочей Windows-машины. Для этого использовал встроенный туннель `port-forward` прямо на порт сервиса Графаны:
  ```bash
  k port-forward -n monitoring svc/kube-prom-grafana 8080:80
  ```
  После чего успешно заходил в админку через браузер по адресу `http://localhost:8080`.

## ⚠️ Что нужно доработать до уровня Production (Технический долг)
Данный проект — это локальный self - hosted для обкатки стека в изолированной среде. Для деплоя в реальный продакшен необходимо закрыть следующие задачи:
1. **Безопасность (RBAC & Secrets):**
* Внедрить полноценный GitOps-подход к управлению секретами.
* Для выкатки в прод необходимо полностью исключить хардкод из values-файлов и интегрировать кластер с Mozilla SOPS / Bitnami Sealed Secrets (для хранения зашифрованных секретов в Git) или развернуть HashiCorp Vault.
2. **Мониторинг хоста:**
   * Разобраться с контекстом безопасности (SecurityContext) для `node-exporter`, чтобы он мог корректно собирать системные метрики Linux-хоста без падения по правам доступа.
3. **Сетевой уровень и Доступ:**
* Развернуть и настроить локальный DNS-сервер (CoreDNS или dnsmasq) с поддержкой Wildcard-записей (*.kube.local). Это позволит автоматизировать резолв доменов для новых микросервисов на машинах разработчиков и отказаться от ручной подмены HTTP-заголовков через curl.
4. **Архитектура манифестов:**
* Декомпозировать монолитный манифест app.yaml на отдельные сущности. Упаковать приложение в кастомный Helm-чарт для параметризации конфигураций под разные окружения (Dev/Stage/Prod). После миграции — перевести шаг валидации в GitVerse CI с kube-linter на helm lint.
5. **Направления развития CI/CD (Next Steps):**
- [ ] Наполнить репозиторий реальными values-файлами мониторинга и убрать заглушки из шага валидации.
- [ ] Добавить стадию автоматического деплоя (`CD`) в K3s-кластер через `helm upgrade --install` после успешного прохождения линтеров.
