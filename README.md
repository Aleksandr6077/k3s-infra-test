K3s: Деплой, Мониторинг и Логирование

Пошаговый проект по развертыванию веб-приложения в легковесном Kubernetes (K3s) с настройкой базового мониторинга и сбором логов. 

## ⚙️ Что внутри проекта
* **Кластер**: K3s
* **Приложение**: Веб-сервер Nginx (с ограничением по CPU/памяти и постоянным диском)
* **Мониторинг**: Prometheus + Grafana (установка через Helm)
* **Логирование**: Grafana Loki + Promtail (установка через Helm)

---

## 🛠️ Как это устроено (По шагам)

### 1. Подготовка окружения (CLI)
Чтобы не писать длинные команды, настроил алиас для kubectl и скопировал конфиг для доступов:
```bash
alias k='k3s kubectl'
mkdir -p ~/.kube && sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown $(id -u):$(id -g) ~/.kube/config
```
Для удобного просмотра подов в терминале установил утилиту **K9s**.

### 2. Запуск приложения (`apps/my-nginx/app.yaml`)
Монолитный YAML-манифест, который поднимает:
* **Deployment**: Запускает контейнер Nginx. Прописал ему лимиты ресурсов (`limits: memory: 64Mi`), чтобы контейнер не сожрал всю память сервера.
* **Service & Ingress**: Маршруты, чтобы пустить трафик к сайту.
* **PersistentVolumeClaim (PVC)**: Подключил к Nginx постоянный диск на 1 Гб (`storageClassName: local-path`), чтобы файлы сайта (index.html) не стирались при перезапуске контейнера.

### 3. Мониторинг (Prometheus + Grafana)
Поставил стек `kube-prometheus-stack` через Helm. Настроил кастомный конфиг `mon-values.yaml`:
* Отключил тяжелый `node-exporter` (сбор метрик самого железа хоста). Оставил только метрики самого Kubernetes. Отключено, так как в K3s по умолчанию нет прав на чтение /proc и /sys без настройки SecurityContext.
* Задал пароль `admin/admin` для входа.

### 4. Сбор логов (Loki + Promtail)
* Поставил базу данных логов **Loki** в легком режиме `SingleBinary` (конфиг `loki-values.yaml`). Выбран режим SingleBinary для упрощения развертывания в изолированной среде (один контейнер вместо трех: loki, querier, distributor). В продакшене этот режим не рекомендуется из-за единой точки отказа.
* Поставил агента **Promtail**, который собирает текстовые логи со всех контейнеров и шлет их в Loki.
* Подключил Loki как Data Source внутри Grafana.

## 🛡️ Локальная безопасность и валидация (Pre-commit | Trivy)
В проекте настроена автоматическая проверка кода перед коммитом с помощью pre-commit хуков.
Подключенные хуки:
* docker-compose-check — автоматическая валидация структуры и синтаксиса файлов Docker Compose.
* Check for Hardcoded Secrets — Trivy

## ⚙️ Автоматизация и CI/CD
В проекте настроен автоматический пайплайн валидации изменений (`.gitea/workflows/ci.yaml`), который триггерится на каждый push в ветку master.
* **Secret Scanning:** Автоматический аудит истории коммитов на утечку паролей с помощью `Gitleaks`.
* **Linting & Syntax:** Автоматическая проверка синтаксиса YAML-манифестов с помощью `PyYAML`.
* **Kube-score (Линтер манифестов):** Проверяет манифесты на соответствие лучшим практикам(заглушка).
* **Kubernetes Dry-Run** Валидация на кластере(заглушка).

### 🔄 Этапы пайплайна (Job: validate):
1. Локальный этап (WSL2)
📥 git commit — фиксация изменений.
🛡️ pre-commit хуки:
 - Trivy — поиск уязвимостей в коде/зависимостях.
 - docker-compose-check — валидация конфигурации Docker Compose.

Если проверки пройдены успешно:
🚀 git push ➡️ Отправка изменений в GitVerse Repo.

2. Удалённый этап (CI/CD)
При поступлении коммита в master запускается Gitverse `Job 'validate`, который параллельно выполняет три проверки:
🔑 Gitleaks — сканирование репозитория на утечку секретов (пароли, токены).
📄 pyyaml — синтаксическая проверка всех YAML-файлов.
☸️Kube-score и ☸️Kubernetes Dry-Run(временно заглушки, записано в тех.долге)

## 🔍 Как я это проверял (Траблшутинг)

* **Костыль для проверки домена**: Когда проверял работу Ingress, домен `my-app.local` не резолвился через DNS хоста. Для валидации работы Ingress-ресурса при отсутствии настроенного DNS был использован curl с принудительным указанием заголовка Host.
  ```bash
  curl -H "Host: my-app.local" http://127.0.0.1
  ```
* **Проверка Графаны с Windows**: Так как K3s крутится на отдельном сервере, я проверял графики и логи со своей рабочей Windows-машины. Для этого использовал встроенный туннель `port-forward` прямо на порт сервиса Графаны:
  ```bash
  k port-forward -n monitoring svc/kube-prom-grafana 8080:80
  ```
  После чего успешно заходил в админку через браузер по адресу `http://localhost:8080`.
