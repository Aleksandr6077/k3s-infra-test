### ⚠️ Осознанные компромиссы и архитектурные ограничения (Trade-offs)

При проектировании этой HA-архитектуры был сделан осознанный выбор в пользу встроенного консенсуса k3s (вместо классического выделенного кластера `etcd`), что накладывает определенные ограничения, которые необходимо учитывать:

‼️ ‼️‼️Корректировка мультизоны в файле [![multi-zonal-limitation](./docs/multi-zonal-limitation)](./docs/multi-zonal-limitation)

#### 1. **Отсутствие глубокого опыта с классическим `etcd`**:
   В данной схеме мы не настраиваем `etcd` вручную «с нуля» (с генерацией TLS-сертификатов, управлением снапшотами базы через `etcdctl` и тонкой настройкой кворума). Мы доверились абстракции k3s, которая берет это на себя под капотом. Для полноценного Production на «большом» Kubernetes ручная работа с `etcd` является обязательным навыком.

#### 2. **Производительность встроенного консенсуса (Embedded etcd)**:
   K3s использует встроенный в бинарник движок `etcd` для организации распределенного консенсуса Raft между тремя мастер-нодами. На реальном высоконагруженном продакшене со стабильно высокой интенсивностью записи (сотни подов, частые мутации ресурсов) встроенный embedded-кластер может уступать по производительности и пропускной способности выделенному, изолированному кластеру `etcd`, вынесенному на отдельные bare-metal или compute-ноды.

#### 3. **Связанность Control Plane и State**:
   В нашей схеме компоненты управления кластером (API Server, Controller Manager) и база данных (State) живут внутри одних и тех же контейнеров. В Enterprise-архитектурах базу данных (`etcd`) принято выносить на абсолютно независимые, изолированные серверы, чтобы высокая нагрузка на API-сервер не приводила к потере кворума и деградации базы.

#### 4. **preemptible ноды**:
мастера и воркеры — прерываемые (`preemptible`) VM.

**Что это даёт:**
- Стоимость стенда ~20-40 ₽ за 2 часа вместо ~200 ₽.
- Приемлемо для эфемерного стенда.

**Что это ломает:**
- `HA`обеспечивается на уровне workload'ов (Deployment, CNPG Cluster, Longhorn replicas),
  но **не на уровне инфраструктуры**.
- Реклейм VM облаком → Pod пересоздаётся на другой ноде.
  Для `stateless`-сервисов это незаметно, для `stateful` (PG, Longhorn) — это **failover**.
- Failover при реклейме VM — **ожидаемое поведение, не баг**.


#### 5. **Bastion-only доступ вместо публичного NLB**

  - На старте проекта было принято решение `не публиковать Kubernetes API
(6443) в интернет и не использовать внешний NLB`. Вместо этого —
доступ через `bastion-хост и SSH-туннель`.

   **Причины:**
1. **Экономия:** публичный IP + NLB = ~ публичный **статический** IP + NLB = ~250–300 ₽/мес на эфемерном стенде,
   который поднимается на несколько часов в сутки.
2. **Безопасность:** API-сервер не виден из интернета, SG ограничивает
   доступ только доверенными IP.
3. **Простота:** нет нужды настраивать ALB/NLB для L4-трафика
   `(Yandex NLB с приватными мастерами требует публичных IP).`

**Что это даёт:** дешёвый, безопасный, воспроизводимый стенд.

**Что это ломает:** автоматизацию CI/CD с публичными раннерами.
Для production потребуется один из вариантов:
- `Внешний NLB + публичные IP мастеров + SG по IP раннеров.`
- `Self-hosted ARC (Actions Runner Controller) внутри VPC — без публичных IP.`
- `VPN в VPC + internal NLB.`

*Данный компромисс был выбран осознанно ради минимизации стоимости эфемерного стенда (публичный IP + NLB = ~250–300 ₽/мес), а также для повышения безопасности (API-сервер не виден из интернета).

**В production-инфраструктуре** будет выбран один из перечисленных выше вариантов (NLB + публичные IP, ARC, или VPN).*

### 6 **Bastion-проблема SPOF**

 - Бастион — прерываемая ВМ. Риск остановки в момент деплоя минимален, но существует. В продакшне бастион должен быть на обычной ВМ!

### 7. **Longhorn для HA-хранилища**

Для обеспечения отказоустойчивости данных при миграции подов между нодами
был выбран **Longhorn** вместо **Rook-Ceph**.

**Причины:**
- **Rook-Ceph** требует минимум 3 ноды с 8+ ГБ RAM и выделенными NVMe-дисками.
  На нашем стенде (5 нод по 4 ГБ RAM, прерываемые) Ceph будет нестабилен
  и съест все ресурсы при rebalancing.
- **Longhorn** создан для небольших кластеров (k3s, edge). Не требует
  выделенных сырых дисков, работает как набор микросервисов.
- **Установка за 10 минут** через Helm, есть веб-интерфейс для мониторинга реплик.

**Что это даёт:**
- **2 реплики** каждого тома (можно потерять 1 ноду без потери данных).
- **Автоматическое восстановление** реплик при падении ноды.
- **Бэкап в S3** (Object Storage) для сохранения данных между сессиями.

**Ограничения:**
- **Только `ReadWriteOnce` (RWO)** — блокируется на одну ноду. Для
  `ReadWriteMany` (RWX) потребуется встроенный NFS-сервер Longhorn
  (менее эффективно, чем CephFS).
- **2 реплики вместо 3** — компромисс для слабых нод (экономия места).
- **В продакшне** Longhorn должен управляться через **ArgoCD (GitOps)**,
  а не через Ansible. Ansible ставит его только для bootstrap эфемерного стенда.

## 🏗 Что внутри проекта (🌐 Архитектура облачного стенда)

* **Кластер**: K3s (Multi-Zonal**** HA-кластер с 3 мастер-нодами + 2 воркер-нодами)
  - Мастера распределены по трём зонам: `ru-central1-a`, `ru-central1-e`, `ru-central1-d`
  - Воркеры — в зонах `ru-central1-a`, `ru-central1-e`
* **Приложение**: Веб-сервер Nginx (с ограничением по CPU/RAM и постоянным диском)
* **GitOps**: ArgoCD (установка из официального манифеста, синхронизация приложений из Git)
* **Мониторинг**: Prometheus + Grafana (установка через Helm)
* **Логирование**: Grafana Loki (установка через Helm)
* **Эфемерный стенд и S3**: Бакет Object Storage живёт отдельно от стенда и **не удаляется** при `make down`.

**Multi-Zonal** Инфраструктурная мультизональность (3 зоны для мастеров). Логическая мультизональность в Kubernetes (метки зон) — в техдолге (требует Yandex CCM)

### Сетевая архитектура

* **`k3s-bastion`** — Точка входа для SSH и управления кластером.
  - Публичный IP: динамический
  - Внутренний IP: `10.200.1.x`
* **Мастер-ноды** (`k3s-master-1`, `k3s-master-2`, `k3s-master-3`) — приватные, прерываемые без публичного IP:
  - `k3s-master-1`: `10.200.2.x` (зона `ru-central1-a`)
  - `k3s-master-2`: `10.201.2.x` (зона `ru-central1-e`)
  - `k3s-master-3`: `10.202.2.x` (зона `ru-central1-d`)
* **Воркер-ноды** (`k3s-worker-1`, `k3s-worker-2`) — приватные, без публичного IP:
  - `k3s-worker-1`: `10.200.3.x` (зона `ru-central1-a`)
  - `k3s-worker-2`: `10.201.3.x` (зона `ru-central1-e`)
* **Доступ к API**: через SSH-туннель до мастера (через bastion).
* **NAT-шлюз**: для выхода приватных нод в интернет (за образами, обновлениями).

**Полная Схема Доступна в файле `docs/architecture.md`**

    (ввиду недоступности зоны b - схему оставил старую, на 3 зоны)

**🔑 Ключевые особенности схемы:**

1. **Разделение точек входа (Безопасный периметр)**: Весь административный трафик (SSH и Kubernetes API) полностью изолирован от внешнего мира и доступен строго через выделенный бастион-хост (`k3s-bastion`). Прямой доступ к API-серверу (порт 6443) снаружи закрыт — `kubectl` работает через SSH-туннель (`ssh -J bastion -L 6443:127.0.0.1:6443 master`). Веб-сервисы (80/443) пока доступны только внутри кластера (Ingress — в планах).

2. **Гибридный сетевой контур (Public & Private Subnets)**: Сеть разделена на три пула:
   - **Публичная подсеть** `********` — для бастиона (единственная ВМ с публичным IP).
   - **Приватная подсеть мастеров** `10.200.2.0/24` — для 3 мастер-нод (HA-кворум).
   - **Приватная подсеть воркеров** `10.200.3.0/24` — для 2 воркер-нод (приложения).

   Межнодовый трафик внутри подсетей разрешён в Security Group для работы etcd и Flannel CNI. Мастера и воркеры закрыты от прямого доступа из внешнего мира и ходят в интернет строго через NAT-шлюз.

3. **Эфемерность нод при неизменной точке входа**: Все ВМ — прерываемые (`preemptible = true`), их можно полностью уничтожить и пересоздать (`make down` / `make up`). Доступ к кластеру осуществляется через бастион, IP которого **меняется** при пересоздании, но это не требует ручной перенастройки конфигов: перед работой ты запускаешь SSH-туннель (одной командой), и `kubectl` работает через `127.0.0.1:6443`.

## ⚙️ Как это устроено:
### Описание доступа к сервисам с управляющего хоста (WSL2):

* **Доступ к Kubernetes API (через SSH-туннель):** API-сервер (6443) не опубликован в интернет. Доступ с хост-машины — через SSH-туннель до bastion, который проксирует трафик на одну из мастер-нод.

* **Локальная отладка и диагностика (Port Forwarding):** Для доступа к веб-интерфейсам инфраструктуры и отладки без публикации их через `Ingress` используется `kubectl port-forward`. Не для production — инструмент для локальной отладки; Это позволяет работать с сервисами на localhost:<port> без правки `DNS/hosts`.

* **Эфемерность и борьба с дрейфом:** Для экономии ресурсов и исключения конфигурационного дрейфа вся инфраструктура спроектирована как эфемерная (Ephemeral). Кластер разворачивается строго под рабочую сессию с помощью `make up`(нарезка виртуалок диски и тд) `make ansible-deploy` (отрабока плейбука) и полностью уничтожается командой `make down`.

## Рабочий процесс (Как ведется работа над проектом)

- Регулярность: коммичу часто, не коплю изменения. Мелкие правки — по ходу, крупные апдейты — раз в месяц.
- Ветки: `feature`-ветки под крупные задачи, `infra-tests`-для тестов,  `squash`-мерж в `master` с осмысленным сообщением.
- Документация: `CHANGELOG` `README` `failure-modes` `SLO` и `trade-offs`
- Автоматизация: линтеры в `CI` (`yamllint, Gitleaks, Trivy, kube-score`), `pre-commit hooks`.
- Ревью: self-review, приветствую внешний фидбек.
- Стиль: предпочитаю понятные решения сложным, документирую компромиссы.


### Команды управления

1. **Поднятие инфраструктуры в облаке (OpenTofu):**
   Развернуть виртуальные машины, сеть VPC, группы безопасности и нативный балансировщик трафика в Yandex Cloud:
   ```bash
   make up
   ```

2. **Конфигурация кластера (Ansible):**
   Настроить кластер k3s на развернутых нодах, автоматически импортировать доступы (`kubeconfig`)

   ```bash
   make ansible-deploy
   ```

---

### 2. Запуск приложения (`k8s/apps/nginx/`)

Приложение упаковано в **Helm-чарт** для параметризации и переиспользования:

- **`Chart.yaml`** — метаданные чарта.
- **`values.yaml`** — параметры (образ, реплики, ресурсы, storage, service, ingress).
- **`files/index.html`** — статический контент (вынесен из `values.yaml`).
- **`templates/`** — шаблоны манифестов:
  - `pvc.yaml` — постоянный диск на 1 ГБ (`storageClassName: local-path`).
  - `deployment.yaml` — 2 реплики приложения под управлением non-root образа `nginxinc/nginx-unprivileged:1.25-alpine` (порт `8080`). Настроены лимиты ресурсов, `podAntiAffinity` против SPOF ноды и `preStop` хук для Graceful Shutdown.
  - `configmap.yaml` — ConfigMap с `index.html` (монтируется в init-контейнер).
  - `service.yaml` — внутренний балансировщик (ClusterIP).
  - `ingress.yaml` — правила маршрутизации Traefik для внешнего доступа по адресу `http://my-app.local`.
  - `_helpers.tpl` — шаблоны имён и меток.


### 3. GitOps

Приложения и платформенные компоненты управляются через **ArgoCD** :
- **`k8s/platform/argocd-apps/nginx-app.yaml`** — ArgoCD Application для Nginx (Helm-чарт).
- **`k8s/platform/argocd-apps/monitoring-app.yaml`** — ArgoCD Application для `kube-prometheus-stack` (Helm-чарт)
- **`k8s/platform/traefik-config.yaml`** — HelmChartConfig для фиксации NodePort Traefik (`30080`/`30443`).

### 4. Мониторинг

- Стек `kube-prometheus-stack` ставится через **ArgoCD Application** (`monitoring-app.yaml`).
- Кастомный конфиг — **`k8s/platform/monitoring/values.yaml`** (заменяет старый `mon-values.yaml`).
- **Отключены тяжелые компоненты** (`kubeEtcd`, `kubeControllerManager`, `kubeScheduler`, `kubeProxy`) — не нужны на эфемерном стенде.
- **Безопасность учётных данных:** все чувствительные данные (пароль Grafana, Telegram-токены) вынесены из публичного репозитория, зашифрованы через **Ansible Vault** и динамически подставляются в процессе деплоя.
- **Telegram-нотификации:** Alertmanager отправляет алерты в Telegram (receiver `telegram_configs`, токены из Secret `alertmanager-telegram`).
- **Alert rules:** `NodeDown`, `PodCrashLooping`, `HighCPU`.

### 5. 🛡️ Локальная безопасность и валидация (Pre-commit)

В проекте настроена автоматическая проверка кода перед коммитом(`.pre-commit-config.yaml`)

### 6. ⚙️ Автоматизация и CI/CD

Реализован пайплайн статического анализа кода и безопасности (`/workflows/ci.yaml`), триггерится на `push` и `pull_request` в `master`.

### 🔄 Этапы пайплайна:
- **Linting & Syntax (yamllint):** проверка синтаксиса YAML-файлов (Ansible-роли, Kubernetes-манифесты).
- **Secret Scanning (Gitleaks):** аудит истории коммитов на утечки чувствительных данных.
- **IaC Security Scanner (Trivy):** статический анализ OpenTofu (Terraform) и Ansible.
- **K8s Best Practices (Kube-score):** линтинг манифестов на best practices.
- **Notifications (Telegram API):** алертинг о статусе сборки.
