## 🏗️ K3s: Деплой, Мониторинг и Логирование🏗️

Проектирование, автоматизация развертывания (IaC/Ansible) и траблшутинг микросервисного кластера k3s со стеком мониторинга и логирования.

---

### ⚠️ Осознанные компромиссы и архитектурные ограничения (Trade-offs)

При проектировании этой HA-архитектуры был сделан осознанный выбор в пользу встроенного консенсуса k3s (вместо классического выделенного кластера `etcd`), что накладывает определенные ограничения, которые необходимо учитывать:

1. **Отсутствие глубокого опыта с классическим `etcd`**: 
   В данной схеме мы не настраиваем `etcd` вручную «с нуля» (с генерацией TLS-сертификатов, управлением снапшотами базы через `etcdctl` и тонкой настройкой кворума). Мы доверились абстракции k3s, которая берет это на себя под капотом. Для полноценного Production на «большом» Kubernetes ручная работа с `etcd` является обязательным навыком.

2. **Производительность встроенного Raft (Kine)**:
   k3s использует встроенный механизм, который транслирует вызовы Kubernetes API в распределенную базу данных SQLite/Raft через прослойку Kine. На реальном нагруженном продакшене с сотнями подов этот механизм может уступать по производительности, скорости записи и пропускной способности чистому, выделенному кластеру `etcd`.

3. **Связанность Control Plane и State**:
   В нашей схеме компоненты управления кластером (API Server, Controller Manager) и база данных (State) живут внутри одних и тех же контейнеров. В Enterprise-архитектурах базу данных (`etcd`) принято выносить на абсолютно независимые, изолированные серверы, чтобы высокая нагрузка на API-сервер не приводила к потере кворума и деградации базы.

*Данный компромисс был выбран осознанно ради экономии ресурсов CPU/RAM в локальной среде WSL2 и для быстрой симуляции отказоустойчивости.*

## 🌐 Сетевая архитектура локального стенда (WSL2)
Так как весь стенд разворачивается внутри изолированного Docker-окружения на WSL2, трафик от хост-машины (Windows) до конечных подов Kubernetes проходит следующую цепочку маршрутизации:
```text
       [ Windows Хост (Браузер / CLI) ]
                       │
                       ▼  (localhost / 127.0.0.1)
  ┌─────────────────────────────────────────────────────────┐
  │ WSL2 Окружение (Инфраструктура Docker)                  │
  │                                                         │
  │  [ HAProxy Балансировщик ] (Слушает хост-порты 6443/80) │
  │          │                                              │
  │          ▼ (Внутренняя сеть Docker Bridge: 172.20.0.0/16)
  │   ┌──────────────────────┬──────────────────────┐       │
  │   ▼                      ▼                      ▼       │
  │ [k3s-master-1]       [k3s-master-2]       [k3s-master-3]│
  │ (172.20.0.11)        (172.20.0.12)        (172.20.0.13) │
  │   │                      │                      │       │
  │   └──────────────────────┼──────────────────────┘       │
  │                          ▼                              │
  │              [ Внутренняя сеть K3s Pods ]               │
  │            (Трафик приложений, Loki Prom)               │
  └─────────────────────────────────────────────────────────┘
```
**Ключевые особенности схемы:**
1. **HAProxy как точка входа:** Локальный балансировщик привязывается к интерфейсу `127.0.0.1` (и пробрасывает порты на WSL2 хост), перехватывает запросы от основной системы и равномерно распределяет их между тремя мастерами.
2. **Изолированная подсеть `172.20.0.0/16`:** Эти адреса выделены Docker-движком через `bridge` специально для нашей сети `k3s-net`. Они изолированы от внешней Windows-системы, но HAProxy связывает их с внешним миром

## 🛠️ Как это устроено:
						Описание доступа к сервисам в WSL2:
### Доступ к сервисам и маршрутизация трафика

* **Балансировка Control Plane (L4):** Внешний балансировщик HAProxy распределяет TCP-трафик на порт `6443` между тремя мастер-нодами кластера, обеспечивая отказоустойчивый доступ к Kubernetes API со стороны хост-машины (Windows).
* **Локальная отладка и диагностика (Port Forwarding):** Для изоляции веб-интерфейсов инфраструктуры (например, Grafana в namespace `monitoring`) и работы в обход публичных слоев маршрутизации используется прямое L4-пробронирование портов через команду `kubectl port-forward`. Это исключает необходимость ручной правки DNS/hosts на хосте и обеспечивает прямой защищенный туннель к сервисам.
* **Архитектура публикации приложений (L7 Ingress):** Манифесты содержат декларативное описание правил Ingress для контроллера Traefik (например, домен `my-app.local`), подготавливая архитектуру приложений к бесшовному переходу на полноценную внешнюю L7-маршрутизацию в будущем.
* **Эфемерность и борьба с дрейфом (Configuration Drift):** Для экономии ресурсов хоста и исключения конфигурационного дрейфа вся инфраструктура спроектирована как эфемерная (Ephemeral). Кластер разворачивается строго под рабочую сессию и полностью уничтожается командой `make down` по её окончании.

## 🤖 Автоматизация развертывания через Ansible
Чтобы не выполнять рутинные операции в консоли вручную, базовая подготовка окружения автоматизирована. Написан идемпотентный плейбук, который выполняет:

* Настройку WSL2: создание рабочего окружения для управления кластером Kubernetes.
* Установку утилит: развертывание консольного интерфейса управления K9s и создание alias для kubectl.
* Доставку Kubeconfig: экспорт конфигурации из изолированного контейнера без использования Python на целевом хосте.
* Адаптацию сети: автоматическое перенаправление трафика kubectl на локальный балансировщик (HAProxy).

### Архитектурные особенности автоматизации:
* Без использования SSH `(ansible_connection: docker)`: Сборка адаптирована для работы напрямую с контейнерами через Docker API. Это исключает необходимость настройки SSH-ключей и запуска SSHD внутри контейнеров кластера.
* Запуск без Python-окружения `(ansible_python_interpreter: /bin/sh)`: В мастер-нодах K3s используется минималистичный образ (Alpine/микро-дистрибутивы) без установленного Python. Команды выполняются через встроенный бинарник командного интерпретатора с помощью модуля raw.
* Идемпотентность: Повторные запуски плейбука безопасны. Скачивание K9s и замена строк в файлах конфигурации происходят только при наличии реальных изменений.

## Инструкция по запуску:
							Быстрый старт (Automation)

Управление стендом осуществляется из корня репозитория с помощью утилиты `make`. 

*(Если утилита не установлена в вашей системе, выполните: `sudo apt update && sudo apt install make -y`*

### Команды управления

Развернуть весь HA-кластер с нуля, установить локальные утилиты разработчика (K9s) и импортировать доступы (`kubeconfig` подцепится автоматически):
```bash
make up
```
*(Потребуется ввести пароль sudo для локальной установки пакета K9s на хосте).*

Полностью уничтожить кластер, очистить Docker-тома с Raft-базой данных и безопасно удалить локальный контекст доступа:
```bash
make down
```
*Примечание: В отличие от старой версии, команда `make down` больше не удаляет ваш глобальный файл `~/.kube/config`. Она точечно вырезает только сущности локального стенда (`k3s-local`), бережно сохраняя все остальные ваши рабочие контексты и доступы к другим кластерам.*


Полная пересборка стенда (down + up) одной командой:
```bash
make recreate
```

### 2. Запуск (`apps /my-nginx /app.yaml`)
Монолитный YAML-манифест(не лучшая практика, в техдолг добавил), который поднимает:
* **Deployment**: Запускает контейнер Nginx. Прописал ему лимиты ресурсов (`limits: memory: 64Mi`), чтобы контейнер не сожрал всю память сервера.
* **Service & Ingress**: Маршруты, чтобы пустить трафик к сайту.
* **PersistentVolumeClaim (PVC)**: Подключил к Nginx постоянный диск на 1 Гб (`storageClassName: local-path`), чтобы файлы сайта (index.html) не стирались при перезапуске контейнера.
*  При первом деплое тома **PersistentVolumeClaim** создаются абсолютно пустыми. При монтировании такого диска в рабочую директорию Nginx (/usr/share/nginx/html), дефолтный index.html перезаписывается пустотой, что приводит к ошибке 403 Forbidden. Для решения этой проблемы применен паттерн с Init-контейнером:
* Жизненный цикл поды: Kubernetes сначала запускает временный контейнер на базе alpine из блока initContainers.
* Подготовка данных: Контейнер монтирует к себе PVC и выполняет команду записи:
```bash
   echo "<h1>Hello...</h1>" > /data/index.html
   ```
* Передача управления: После успешного выхода (exit 0) Init-контейнера, Kubernetes запускает основной контейнер nginx, который считывает подготовленный файл из того же тома.

### 3. Мониторинг (Prometheus + Grafana)
Поставил стек `kube-prometheus-stack` через Helm. Настроил кастомный конфиг `mon-values.yaml`:
* Отключил тяжелый `node-exporter` (сбор метрик самого железа хоста). Оставил только метрики самого Kubernetes. Отключено, так как в K3s по умолчанию нет прав на чтение /proc и /sys без настройки SecurityContext.
* Задал пароль `admin/admin` для входа.

### 4. Сбор логов (Loki)
* Поставил базу данных логов **Loki** в легком режиме `SingleBinary` (конфиг `loki-values.yaml`). Выбран режим SingleBinary для упрощения развертывания в изолированной среде (один контейнер вместо трех: loki, querier, distributor). В продакшене этот режим не рекомендуется из-за единой точки отказа.
* Подключил Loki как Data Source внутри Grafana.

## ⚙️ Автоматизация и CI/CD
В проекте настроен автоматический пайплайн валидации изменений (`...../workflows/ci.yaml`), который триггерится на каждый push в ветку master.
* **Secret Scanning:** Автоматический аудит истории коммитов на утечку паролей с помощью `Gitleaks`.
* **Linting & Syntax:** Автоматическая проверка синтаксиса YAML-манифестов с помощью `PyYAML`.
* **Kube-score (Линтер манифестов):** Проверяет манифесты на соответствие лучшим практикам(заглушка).
* **Kubernetes Dry-Run** Валидация на кластере(заглушка).

## 🔍 Проверка и траблшутинг

* **Локальная проверка Ingress (L7)**: Для валидации работы Ingress-ресурса без настройки системного DNS (файла hosts) использовался локальный запрос через curl с принудительной передачей HTTP-заголовка Host. Это позволило проверить корректность маршрутизации Traefik в обход резолва домена хостом.
  ```bash
  curl -H "Host: my-app.local" http://127.0.0.1:80
  ```
* **Проверка Графаны с Windows**: Так как K3s запущен внутри изолированной среды WSL2, для доступа к веб-интерфейсу мониторинга из браузера Windows был организован временный проброс портов. Трафик туннелировался напрямую к сервису Графаны:
  ```bash
  kubectl port-forward -n monitoring svc/kube-prom-grafana 8080:80
  ```
  После запуска туннеля дашборды и логи стали успешно доступны в браузере хоста по адресу `http://localhost:8080`.
  
 
 ### Сценарий Chaos Engineering (Проверка отказоустойчивости):
1. Запусти `k9s` или выполняй `watch kubectl get nodes`.
2. В соседнем терминале симулируй аварию одной из нод:
   ```bash
   docker compose -f local-infra/docker-compose.yml stop k3s-master-2
   ```
3. Проверь логи HAProxy или сделай запрос к API (`k get nodes`). Кластер продолжит отвечать без прерывания сессии, так как балансировщик перенаправит трафик на оставшиеся 2 ноды, удерживающие кворум.

Данный проект — это локальный self - hosted для обкатки стека в изолированной среде. Для деплоя в реальный продакшен необходимо закрыть следующие задачи:

- [ ] **Стек Мониторинга**: Добавить установку агента Promtail и сделать адаптацию values-файлов под Prometheus, Loki и Node Exporter в условиях распределенного HA-кластера.
- [ ] **Секреты**: Внедрение Mozilla SOPS или HashiCorp Vault
- [ ] Убрать заглушки на этапе работы GitVerse - раннера(Ci.yaml).
- [ ] Декомпозировать монолитный манифест app.yaml на отдельные сущности. Упаковать приложение в кастомный Helm-чарт для параметризации конфигураций под разные окружения (Dev/Stage/Prod).
