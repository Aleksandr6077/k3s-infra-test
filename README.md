K3s: Деплой, Мониторинг и Логирование

Пошаговый проект по развертыванию веб-приложения в легковесном Kubernetes (K3s) с настройкой базового мониторинга и сбором логов. 

## ⚙️ Что внутри проекта
* **Кластер**: K3s
* **Приложение**: Веб-сервер Nginx (с ограничением по CPU/памяти и постоянным диском)
* **Мониторинг**: Prometheus + Grafana (установка через Helm)
* **Логирование**: Grafana Loki + Promtail (установка через Helm)

---

## 🛠️ Как это устроено:
Схема доступа к сервисам в WSL2:
* Продакшн-подобный доступ: Через доменные имена (L7 уровень), которые обрабатывает встроенный в k3s Ingress-контроллер Traefik.
* Отладка и диагностика: Напрямую в обход Ingress с помощью команды kubectl port-forward.

## 🤖 Автоматизация развертывания через Ansible

Чтобы не выполнять рутинные операции в консоли вручную, базовая подготовка окружения автоматизирована. Написан идемпотентный плейбук, который выполняет:
* Скачивание и запуск k3s
* Создание директории `~/.kube` с безопасными правами доступа.
* Копирование конфигурационного файла кластера `k3s.yaml` под `sudo` с автоматической сменой владельца.
* Настройку постоянного системного алиаса `k='k3s kubectl'` в `.bashrc`.
* Чистую установку последней версии терминального интерфейса **K9s** через официальный `.deb` пакет с очисткой временных файлов.

### Инструкция по запуску:
Быстрый старт (Automation)

Управление стендом осуществляется из корня репозитория с помощью утилиты `make`. 

*(Если утилита не установлена в вашей системе, выполните: `sudo apt update && sudo apt install make -y`)*

### 1. Поднятие стенда с нуля
Для автоматической подготовки окружения, установки k3s, настройки конфигурации `kubectl`, создания алиасов и установки консольной утилиты `k9s` выполните:
```bash
make up
```
*Команда автоматически перейдет в рабочую директорию Ansible и запустит плейбук. Поскольку используется флаг `-k`, система остановится и запросит ваш пароль SSH/Sudo перед началом выполнения тасок.*

### 2. Полное уничтожение стенда
После завершения работы для очистки хоста от системных юнитов, контейнеров и виртуальных сетевых интерфейсов выполните:
```bash
make down
```

### 3. Быстрая пересборка (Recreate)
Если вам необходимо сбросить состояние кластера до базового («чистого») вида, выполните команду, которая последовательно снесет старый кластер и развернет новый:
```bash
make recreate
```

### 2. Запуск (`apps /my-nginx /app.yaml`)
Монолитный YAML-манифест(не лучшая практика, в техдолг добавил), который поднимает:
* **Deployment**: Запускает контейнер Nginx. Прописал ему лимиты ресурсов (`limits: memory: 64Mi`), чтобы контейнер не сожрал всю память сервера.
* **Service & Ingress**: Маршруты, чтобы пустить трафик к сайту.
* **PersistentVolumeClaim (PVC)**: Подключил к Nginx постоянный диск на 1 Гб (`storageClassName: local-path`), чтобы файлы сайта (index.html) не стирались при перезапуске контейнера.
*  При первом деплое тома **PersistentVolumeClaim** создаются абсолютно пустыми. При монтировании такого диска в рабочую директорию Nginx (/usr/share/nginx/html), дефолтный index.html перезаписывается пустотой, что приводит к ошибке 403 Forbidden. Для решения этой проблемы применен паттерн с Init-контейнером:
* Жизненный цикл поды: Kubernetes сначала запускает временный контейнер на базе alpine из блока initContainers.
* Подготовка данных: Контейнер монтирует к себе PVC и выполняет команду записи:
```bash
   echo "<h1>Hello...</h1>" > /data/index.html
   ```
* Передача управления: После успешного выхода (exit 0) Init-контейнера, Kubernetes запускает основной контейнер nginx, который считывает подготовленный файл из того же тома.

### 3. Мониторинг (Prometheus + Grafana) (FIXED in CHANGELOG)
Поставил стек `kube-prometheus-stack` через Helm. Настроил кастомный конфиг `mon-values.yaml`:
* Отключил тяжелый `node-exporter` (сбор метрик самого железа хоста). Оставил только метрики самого Kubernetes. Отключено, так как в K3s по умолчанию нет прав на чтение /proc и /sys без настройки SecurityContext.
* Задал пароль `admin/admin` для входа.

### 4. Сбор логов (Loki + Promtail) (FIXED in CHANGELOG)
* Поставил базу данных логов **Loki** в легком режиме `SingleBinary` (конфиг `loki-values.yaml`). Выбран режим SingleBinary для упрощения развертывания в изолированной среде (один контейнер вместо трех: loki, querier, distributor). В продакшене этот режим не рекомендуется из-за единой точки отказа.
* Поставил агента **Promtail**, который собирает текстовые логи со всех контейнеров и шлет их в Loki.
* Подключил Loki как Data Source внутри Grafana.

## ⚙️ Автоматизация и CI/CD
В проекте настроен автоматический пайплайн валидации изменений (`.gitea/workflows/ci.yaml`), который триггерится на каждый push в ветку master.
* **Secret Scanning:** Автоматический аудит истории коммитов на утечку паролей с помощью `Gitleaks`.
* **Linting & Syntax:** Автоматическая проверка синтаксиса YAML-манифестов с помощью `PyYAML`.
* **Kube-score (Линтер манифестов):** Проверяет манифесты на соответствие лучшим практикам(заглушка).
* **Kubernetes Dry-Run** Валидация на кластере(заглушка).

### 🔄 Этапы пайплайна (Job: validate):
1. Локальный этап (WSL2)

## 🔍 Проверка и траблшутинг

* **Локальная проверка Ingress (L7)**: Для валидации работы Ingress-ресурса без настройки системного DNS (файла hosts) использовался локальный запрос через curl с принудительной передачей HTTP-заголовка Host. Это позволило проверить корректность маршрутизации Traefik в обход резолва домена хостом.
  ```bash
  curl -H "Host: my-app.local" http://127.0.0.1:80
  ```
* **Проверка Графаны с Windows**: Так как K3s запущен внутри изолированной среды WSL2, для доступа к веб-интерфейсу мониторинга из браузера Windows был организован временный проброс портов. Трафик туннелировался напрямую к сервису Графаны:
  ```bash
  kubectl port-forward -n monitoring svc/kube-prom-grafana 8080:80
  ```
  После запуска туннеля дашборды и логи стали успешно доступны в браузере хоста по адресу `http://localhost:8080`.

## ⚠️ Что нужно доработать до уровня Production (Технический долг)
Данный проект — это локальный self - hosted для обкатки стека в изолированной среде. Для деплоя в реальный продакшен необходимо закрыть следующие задачи:

0. **Перевод кластера в режим High Availability (HA) и ликвидация SPOF:**
   
**Текущее ограничение (Текущий техдолг):**
На текущем этапе архитектура кластера k3s развернута в минимальной конфигурации: 1 Control Plane (Master-нода) со встроенной СУБД SQLite. Данная схема содержит Single Point of Failure (SPOF) — при выходе из строя единственного мастера нарушается консистентность и управление кластером. 

**План модернизации до уровня Production-ready:**
Для достижения истинной отказоустойчивости инфраструктуры запланирован переход на HA-архитектуру по одному из двух Enterprise-сценариев:

➔. **Сценарий А: Распределенный embedded-кворум (dqlite / Raft)**
   * Развертывание 3 идентичных Control Plane нод.
   * Активация встроенного в k3s механизма распределенной базы данных **dqlite**.
   * Настройка алгоритма консенсуса Raft между мастерами (требуется строго нечетное количество нод, минимум 3, для обеспечения кворума и защиты от Split-Brain).
   * Подключение N воркер-нод к отказоустойчивому пулу мастеров через балансировщик нагрузки (Yandex Network Load Balancer).

➔. **Сценарий Б: Вынос Control Plane State во внешнюю СУБД (External DB)**
   * Направление трафика мастеров на отказоустойчивый внешний кластер **PostgreSQL** (например, Managed Service for PostgreSQL в Yandex Cloud).
   * Развертывание 2 или более Control Plane нод, работающих в режиме Active-Active и считывающих состояние кластера из единого внешнего транзакционного бэкенда.

**Результат модернизации:** Кластер безболезненно переживет потерю любого Control Plane или Worker узла без деградации сервисов и потери конфигурационных данных.
